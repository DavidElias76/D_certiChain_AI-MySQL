03

Class Diagram (UML)

The platform's core entity model with concrete fields and cardinal relationships. Mirrors the MySQL schema and on-chain data structures.

Institution

Tenant root. Each institution owns one authorized issuer wallet on-chain.

User

Any authenticated platform account. Roles: systemAdmin, admin, student, employer.

Certificate

An issued academic credential. The certificate_hash anchors on-chain.

VerificationLog

One row per verification attempt — anchors analytics and audit trails.

Recommendation

AI-generated structured career suggestion stored alongside its certificate source.

CertificateRecord  ·  on-chain (Ethereum)

Solidity struct stored in certificates[hash][institutionId]. Mutability = append + revoke only.

cardinality

Relationships

Institution owns (composes) — users and certificates are scoped under one institution 1 ↔ N each
User (admin) issues — an admin creates many certificate records 1 ↔ N
Certificate anchored by — the certificate_hash + institutionId pair maps to on-chain CertificateRecord 1 ↔ 1
Certificate has many — verification attempts accumulate as one row per request 1 ↔ N
Certificate yields — one AI recommendation record per certificate (cascade delete) 1 ↔ 0..1
04

Notes

Three diagrams, three audiences: context for stakeholders, component view for engineering leads, UML class diagram for DB / API alignment.

Why these diagrams

The context diagram answers "who is outside the system?" — the UML class diagram answers "what does the system remember?" — the component diagram answers "where does work happen?"

Multi-tenancy

Every certificate record is scoped by institutionId. The compound key (certificateHash, institutionId) is the unique axis across both MySQL and the smart contract.

On-chain authority

Only the wallet registered for an institutionId may call issueCertificate / revokeCertificate. The contract owner registers institutions; everything else is enforced by onlyAuthorizedIssuer.
